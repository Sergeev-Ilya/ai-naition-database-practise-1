# Spec Delta

## Purpose

Определяет проверяемый контракт создания, дедупликации и надежного хранения записей, содержащих имя и телефон.

## ADDED Requirements

### Requirement: Формат записи
Система SHALL хранить `id`, `name`, `phone`, `createdAt`. `id` SHALL быть UUID, `createdAt` — UTC в ISO 8601. Имя после удаления пробелов по краям SHALL содержать 1–200 символов. Телефон SHALL соответствовать E.164: `+` и 8–15 цифр, первая цифра не `0`.

#### Scenario: Корректные данные
- **WHEN** переданы `name="Иван Петров"` и `phone="+79991234567"`
- **THEN** система принимает запись и сохраняет имя без изменения регистра

#### Scenario: Некорректные данные
- **WHEN** имя пустое или телефон не соответствует E.164
- **THEN** система отклоняет запрос с HTTP `400` и кодом `VALIDATION_ERROR`

### Requirement: API создания записи
Система SHALL предоставлять `POST /api/v1/contacts` с JSON-телом `{"name": string, "phone": string}`. Обработка SHALL идти этапами: проверка формата, нормализация, проверка дубля, атомарная запись, формирование ответа.

#### Scenario: Запись создана
- **WHEN** клиент передает корректную новую комбинацию имени и телефона
- **THEN** API возвращает HTTP `201` и JSON `{"id": UUID, "name": string, "phone": string, "createdAt": string}`

#### Scenario: Неизвестное поле
- **WHEN** JSON содержит поле вне контракта
- **THEN** API возвращает HTTP `400` и код `VALIDATION_ERROR`

### Requirement: Защита от дублей
Система MUST считать дублем совпадение имени без учета регистра и пробелов по краям вместе с полным совпадением нормализованного телефона. Проверка и создание SHALL выполняться атомарно.

#### Scenario: Повторная комбинация
- **WHEN** комбинация нормализованных имени и телефона уже существует
- **THEN** API возвращает HTTP `409`, код `CONTACT_ALREADY_EXISTS` и сообщение `Данный телефон и имя уже зарегистрированы`

#### Scenario: Совпало только одно поле
- **WHEN** совпадает только имя или только телефон
- **THEN** система создает отдельную запись

### Requirement: Единый формат ошибок
Все ошибки API SHALL иметь JSON-формат `{"code": string, "message": string, "details": object}` и заголовок `Content-Type: application/json`.

#### Scenario: Ошибка запроса
- **WHEN** API отклоняет запрос клиента
- **THEN** ответ содержит непустые `code` и `message`, а `details` содержит ошибки по полям либо пустой объект

### Requirement: Сохранность данных
После ответа HTTP `201` запись MUST сохраняться без потери при штатном перезапуске приложения или хранилища. Система SHALL поддерживать не менее 1 000 000 записей.

#### Scenario: Перезапуск после успешной записи
- **WHEN** запись получила ответ HTTP `201` и система штатно перезапущена
- **THEN** запись доступна для поиска после запуска

#### Scenario: Миллион записей
- **WHEN** в базе хранится 1 000 000 валидных записей
- **THEN** создание и поиск продолжают соответствовать своим контрактам и SLA

### Requirement: Производительность создания
При базе до 1 000 000 записей и нагрузке 100 запросов в секунду API SHALL обрабатывать не менее 99% запросов создания за 50 мс, без учета сетевой задержки клиента. Стенд: приложение — 2 vCPU/2 GiB RAM, СУБД — 2 vCPU/4 GiB RAM и SSD, RTT между ними до 1 мс.

#### Scenario: Нагрузочная проверка создания
- **WHEN** после 2 минут прогрева в течение 10 минут подается 100 запросов создания в секунду на эталонном стенде
- **THEN** p99 серверного времени ответа не превышает 50 мс и доля HTTP `5xx` не превышает 0,1%
