# Spec Delta

## Purpose

Определяет единый и измеримый контракт поиска контактов по имени или телефону для программных клиентов и веб-интерфейса.

## ADDED Requirements

### Requirement: API поиска
Система SHALL предоставлять `GET /api/v1/contacts` ровно с одним параметром `name` или `phone`. Допустимы `limit` от 1 до 1000, по умолчанию 100, и непрозрачный `cursor`. Обработка SHALL идти этапами: проверка параметров, нормализация, поиск, формирование страницы результатов.

#### Scenario: Поиск телефонов по имени
- **WHEN** клиент передает только `name`
- **THEN** API возвращает HTTP `200` и записи с точным совпадением нормализованного имени без учета регистра

#### Scenario: Поиск имен по телефону
- **WHEN** клиент передает только `phone`
- **THEN** API возвращает HTTP `200` и записи с точным совпадением нормализованного телефона

### Requirement: Формат результата поиска
Успешный ответ SHALL иметь JSON `{"items": [{"id": UUID, "name": string, "phone": string}], "nextCursor": string|null}`. Каждая запись SHALL встречаться один раз; порядок SHALL быть стабильным по `createdAt`, затем по `id`.

#### Scenario: Найдены записи
- **WHEN** число совпадений не превышает `limit`
- **THEN** `items` содержит все совпадения, а `nextCursor` равен `null`

#### Scenario: Есть следующая страница
- **WHEN** число совпадений превышает `limit`
- **THEN** API возвращает первые `limit` записей и непустой `nextCursor`

#### Scenario: Совпадений нет
- **WHEN** валидный запрос не находит записей
- **THEN** API возвращает HTTP `200`, пустой массив `items` и `nextCursor=null`

### Requirement: Ошибки параметров поиска
При отсутствии критерия, одновременной передаче `name` и `phone`, неверном формате телефона, `limit` или `cursor` система SHALL вернуть HTTP `400` в едином формате ошибок API.

#### Scenario: Критерий не задан
- **WHEN** отсутствуют `name` и `phone`
- **THEN** API возвращает код `SEARCH_CRITERION_REQUIRED`

#### Scenario: Заданы оба критерия
- **WHEN** одновременно переданы `name` и `phone`
- **THEN** API возвращает код `SEARCH_CRITERIA_CONFLICT`

### Requirement: Производительность поиска
При базе до 1 000 000 записей и нагрузке 100 запросов в секунду API SHALL обрабатывать не менее 99% валидных поисковых запросов за 20 мс, без учета сетевой задержки клиента. Стенд: приложение — 2 vCPU/2 GiB RAM, СУБД — 2 vCPU/4 GiB RAM и SSD, RTT между ними до 1 мс.

#### Scenario: Нагрузочная проверка поиска
- **WHEN** после 2 минут прогрева в течение 10 минут подается 100 поисковых запросов в секунду с равномерным сочетанием найденных и пустых результатов на эталонном стенде
- **THEN** p99 серверного времени ответа не превышает 20 мс и доля HTTP `5xx` не превышает 0,1%

### Requirement: Согласованность результата
Успешно созданная запись SHALL быть доступна поиску сразу после ответа HTTP `201`. Незавершенная или отклоненная запись MUST NOT появляться в результатах.

#### Scenario: Чтение после записи
- **WHEN** клиент получает HTTP `201` и сразу выполняет поиск по имени или телефону созданной записи
- **THEN** результат содержит эту запись
